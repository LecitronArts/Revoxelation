# Phase 05.1 Research: Critical Bug Fixes and Safety Hardening

## 1. Current State Assessment

Phase 5 (Bindless Architecture and GPU Scene) just completed. The codebase now has a mature rendering path:
- Vulkan 1.2 with bindless descriptors (10-binding BindlessTable)
- Unified scene_buffer with 4 regions (instances, indirect templates, draw slots, dense indirect)
- GPU frustum + Hi-Z occlusion culling via compute shader
- Dynamic capacity growth (2x doubling)
- Block material system with procedural texture array
- Streaming chunk lifecycle with rayon background jobs
- Greedy meshing with border invalidation

The codebase has **~56 source files** (~4500+ lines of renderer code), extensive `unsafe` usage (150+ unsafe blocks), and several structural patterns that need hardening before further feature work.

---

## 2. Critical Bugs Identified

### BUG-01: Hi-Z Pyramid Not Recreated on Swapchain Resize (CRASH/CORRUPTION)

**Severity: CRITICAL**

`recreate_swapchain_context()` in `swapchain.rs` destroys and recreates the depth image/view, but **does not recreate the Hi-Z pyramid**. The Hi-Z pyramid holds:
- `depth_src_view` — an `ImageView` pointing to the **old** (now destroyed) depth image
- Descriptor sets referencing the old depth image view
- Dimensions (`width`, `height`) matching the old swapchain

After resize, the Hi-Z pyramid samples from a destroyed image, causing **validation errors and potential GPU crash**. The `generate()` dispatch in `submit.rs` will execute with stale descriptors.

**Evidence:** `hiz.rs:183` creates `depth_src_view` from `renderer.swapchain_ctx.depth_image`, but `swapchain.rs:recreate_swapchain_context()` never calls `hiz.recreate()`.

### BUG-02: egui Scratch Buffers GPU-Use-After-Free (CORRUPTION)

**Severity: HIGH**

In `egui_backend.rs`, scratch mesh buffers are uploaded via `StagingBuffer` (which calls `submit_one_shot_commands` with `queue_wait_idle`), then drawn in the **same command buffer** that's being recorded. The buffers are freed at the start of the **next** `paint()` call via `free_stale_scratch()`.

However, with double-buffered frames, frame N's scratch buffers are freed at frame N+1's `paint()`. If frame N's command buffer hasn't finished executing when frame N+1 starts (which is guaranteed since we only wait for frame N+1's fence, not frame N's), the GPU may still be reading from scratch buffers while they're being freed.

**Root cause:** `free_stale_scratch` is called per-paint, not per-frame-fence. With 2 in-flight frames, buffers from frame N-1 may still be in use when frame N+1 frees them.

### BUG-03: submit_one_shot_commands Uses No Fence (RACE CONDITION)

**Severity: MEDIUM-HIGH**

`helpers.rs:190` submits with `vk::Fence::null()` and then calls `queue_wait_idle()`. This blocks the **entire graphics queue**, stalling all in-flight work. While not a data race, this is a correctness concern because:
- It serializes all GPU work during chunk pool growth, texture upload, egui staging copies
- During `grow_capacity()`, this is called between frames — acceptable but suboptimal
- For egui `upload_mesh_scratch()`, this is called **during command buffer recording**, which means queue_wait_idle stalls the queue while a command buffer is being built

### BUG-04: dense_indirect_shadow Bounds Not Checked (POTENTIAL OOB)

**Severity: MEDIUM**

In `chunk_pool.rs:816`:
```rust
self.dense_indirect_shadow[write.draw_index as usize] = write.command;
```
`draw_index` is a `u32` used directly as an index. If a malformed `DenseIndirectWrite` has `draw_index >= capacity`, this panics. While currently the internal logic prevents this, there's no bounds check at the API boundary.

### BUG-05: Camera Distance Always Uses Origin (INCORRECT BEHAVIOR)

**Severity: MEDIUM**

`scheduler.rs:162` hardcodes `camera_pos = [0.0, 0.0, 0.0]` for the streaming camera position, ignoring the actual `FpsCamera` position from `app.rs`. Chunks are always activated/deactivated relative to origin, not the camera position. This means moving the camera doesn't update the streaming active set.

## 3. Safety Issues Identified

### SAFE-01: `unsafe impl Send` for Raw Pointers Without Justification

**Files:** `staging_ring.rs:21,59`, `cull_pipeline.rs:43`

- `StagingAllocation` has `mapped_ptr: *mut u8` and is `unsafe impl Send`
- `StagingRing` has `mapped_base: *mut u8` and is `unsafe impl Send`
- `ChunkCullPipeline` has raw pointers (`frustum_planes_mapped`, `hiz_config_mapped`) and is `unsafe impl Send`

**Risk:** These raw pointers originate from `gpu-allocator` mapped memory. The `Send` impl is correct if the pointers are only written from one thread, but there's no documentation or assertion enforcing this invariant. If `StagingRing` were ever accessed from multiple threads, UB would result.

### SAFE-02: Unchecked .unwrap() in Hot Paths

**Locations (hot path):**
- `job_queue.rs:75,95,109,121` — `Mutex::lock().unwrap()` could panic on poison
- `scheduler.rs:86` — `.unwrap()` on rayon pool build
- `submit.rs:61-62` — `.take().unwrap()` / `.take().expect()` on Option fields during capacity growth

**Impact:** Mutex poisoning from a panic in a rayon thread would crash the main loop. The `.take().unwrap()` pattern is fragile if the execution order changes.

### SAFE-03: `draw_cmd_as_bytes` Uses Manual `from_raw_parts` (UNSAFE)

**File:** `chunk_pool.rs:889-902`

This function reinterprets `DrawIndexedIndirectCommand` as a byte slice via raw pointer cast. While the const assert checks the size, `DrawIndexedIndirectCommand` is not guaranteed by ash to be `#[repr(C)]` without padding. The comment says "caller must ensure repr(C) with no padding" but this is not enforced by the type system.

**Alternative:** bytemuck could be used if `DrawIndexedIndirectCommand` derives `Pod`/`Zeroable`, or the fields could be written individually.

### SAFE-04: ManuallyDrop for Allocator Without Double-Drop Guard

**File:** `mod.rs:67` — `allocator: ManuallyDrop<Allocator>`

The `Renderer::drop()` calls `ManuallyDrop::drop(&mut self.allocator)` at line 287. If `drop()` is called twice (e.g., from a panic during drop), this is UB (double free). While Rust normally prevents calling drop twice, `ManuallyDrop::drop` is explicitly `unsafe` for this reason.

### SAFE-05: No Validation of Shader Push Constant Sizes

Push constants are written with `bytemuck::bytes_of()` but there's no runtime assertion that the byte size matches the pipeline's declared push constant range. Mismatched sizes cause Vulkan validation errors or GPU corruption.

## 4. Hardening Opportunities

### HARD-01: Missing Error Propagation in Drop Implementations

`Renderer::drop()` (mod.rs:184-303) swallows all errors with `let _ = ...`. If allocation freeing fails, the error is silently discarded. While panicking in `drop` is dangerous, logging failures would aid debugging.

**Current pattern:**
```rust
if let Some(egui_backend) = self.egui_backend.take() {
    let _ = egui_backend.destroy(self);
}
```

### HARD-02: Staging Ring Exhaustion Causes Hard Error

If `StagingRing::allocate()` returns `Err` (frame region exhausted), the error propagates up and can fail the entire frame. There's no graceful degradation — no mechanism to defer uploads to the next frame or skip non-critical work.

**Impact:** A single frame with too many chunk deltas will fail entirely rather than processing a partial batch.

### HARD-03: ChunkPool Growth During Command Buffer Recording Window

`submit_frame` checks `needs_grow()` after the fence wait but before command buffer recording. `grow_capacity()` calls `submit_one_shot_commands()` internally, which does `queue_wait_idle`. This is correct for GPU safety, but:
- It blocks the main thread
- It bypasses the staging ring (uses separate one-shot copy commands)
- If growth fails, the error is logged but execution continues with the old capacity — this is correct but should be documented

### HARD-04: Missing Bounds Check on material_ssbo Shader Access

`chunk_mesh.frag:27`:
```glsl
BlockMaterial mat = material_ssbo.materials[v_block_id];
```
There's no bounds check on `v_block_id`. If a chunk contains a block_id beyond the material table size, this reads out-of-bounds GPU memory. The material table has 9 entries (0-8), and `generate_chunk_voxels` generates `pillar_block = 1 + ((seed >> 3) % 8)` which can be 1-8, all valid. But future block editing could introduce invalid IDs.

### HARD-05: Clippy Warnings (38 warnings)

Cargo clippy reports 38 warnings including:
- Unused imports (`Vec4` in camera.rs, `ash::vk` in test files)
- Unused variables (`device` in cull_pipeline, `renderer` in scheduler)
- Unnecessary parentheses and closures
- Collapsible `if` statements
- Field never read (`total_size` in StagingRing)
- Suggestions for `.is_multiple_of()`, `vec![]` macro, simplified `map_or`

These are not bugs but reduce code quality and can mask real issues.

### HARD-06: No Validation Layer Error Handling

`instance.rs:158-170` has a debug callback that logs validation errors, but:
- Validation errors in production builds are silently ignored (no debug_utils)
- There's no mechanism to convert validation errors to runtime errors for testing
- Validation layer presence is not checked — if layers aren't installed, startup succeeds silently

### HARD-07: Event Loop Error Handling is Minimal

`app.rs:300-302` catches `submit_frame` errors with just `log::error!`. If the GPU enters an error state (device lost), subsequent frames will continue to fail. There's no mechanism to:
- Attempt device recovery
- Gracefully exit on unrecoverable errors
- Distinguish between transient and fatal errors

### HARD-08: `SseConfig` Never Updated from RuntimeConfig

`streaming/types.rs` `SseConfig` uses hardcoded `screen_height: 720.0` and `fov_y: PI/3`, never synced with the actual window size or camera FOV. This means SSE-based streaming decisions are based on stale viewport parameters.

## 6. Technical Approach per Requirement

### FIX-01: Hi-Z Resize Recreation

**Approach:** In `recreate_swapchain_context()`, after depth image recreation:
1. If `renderer.hiz_pyramid.is_some()`, take and destroy it
2. Create new `HiZPyramid::new()` with new extent dimensions
3. Re-register the Hi-Z full_view + sampler at bindless binding 7

**Risk:** Low — `HiZPyramid::recreate()` already exists but is never called. The method takes `self` by value, destroys old, creates new.

**Dependencies:** None.

### FIX-02: egui Scratch Buffer Lifetime

**Approach:** Change `scratch_buffers` from a single Vec to a per-frame ring (2 Vecs for 2 in-flight frames):
1. `scratch_buffers: [Vec<(Buffer, Allocation)>; 2]`
2. At `free_stale_scratch`, free the **other** frame's buffers (not the current one)
3. Tie cleanup to `current_frame` index from Renderer

**Alternative:** Use the StagingRing for egui mesh data (CpuToGpu host-visible) and skip GpuOnly + staging for small meshes.

**Risk:** Low — localized change to egui_backend.rs.

### FIX-03: Camera Position Passthrough

**Approach:** Add `camera_pos: [f32; 3]` parameter to `run_world_update()` and `run_frame()`. In `app.rs`, extract camera position from `FpsCamera` and pass it through.

**Risk:** Low — changes function signatures but logic is straightforward.

### FIX-04: dense_indirect Bounds Check

**Approach:** Add `debug_assert!(write.draw_index < self.capacity as u32)` or bounds-checked indexing with `get_mut()` and error return.

**Risk:** Very low.

### FIX-05: Send Safety Documentation

**Approach:** Add `// SAFETY:` doc comments on each `unsafe impl Send` explaining:
- Why the raw pointer is safe to send
- What invariant must hold (single-thread write access)
- Where the invariant is enforced

Optionally: wrap the raw pointer in a newtype that enforces the invariant.

**Risk:** Very low — documentation only.

### FIX-06: draw_cmd_as_bytes Safety

**Approach:** Replace manual `from_raw_parts` with either:
- Individual field writes: `[cmd.index_count.to_le_bytes(), cmd.instance_count.to_le_bytes(), ...]`
- A local `#[repr(C)] #[derive(Pod, Zeroable)]` wrapper struct that copies the fields

**Risk:** Low — the function is used in a few places. Performance impact negligible (5x u32 copy).

### FIX-07: Staging Ring Graceful Degradation

**Approach:** In `record_uploads()`, catch `staging_ring.allocate()` errors:
- If exhaustion occurs mid-batch, stop processing remaining deltas
- Push unprocessed deltas back to the front of `pending_chunk_deltas`
- Log a warning with remaining delta count
- Deltas will be retried next frame

**Risk:** Low — changes are in `chunk_pool.rs:record_uploads()`.

### FIX-08: Clippy Cleanup

**Approach:** Run `cargo clippy --fix` for auto-fixable issues, manually fix the rest:
- Remove unused imports
- Prefix unused variables with `_`
- Apply `.is_multiple_of()` suggestions
- Use `vec![]` macro where suggested
- Simplify `map_or` patterns
- Remove unnecessary parentheses

**Risk:** Very low — mechanical changes.

### FIX-09: Drop Logging

**Approach:** Replace `let _ = expr;` with:
```rust
if let Err(e) = expr {
    log::warn!("failed to cleanup X: {e}");
}
```

**Risk:** Very low — log-only change.

### FIX-10: One-Shot Fence

**Approach:** Create a temporary fence for `submit_one_shot_commands`:
```rust
let fence = device.create_fence(&FenceCreateInfo::default(), None)?;
device.queue_submit(queue, &[submit_info], fence)?;
device.wait_for_fences(&[fence], true, u64::MAX)?;
device.destroy_fence(fence, None);
```

This is functionally equivalent to `queue_wait_idle` but doesn't stall other unrelated submits.

**Risk:** Low — this only matters when multiple queues are in use, which isn't the case currently. Can be deferred.

## 8. Risks and Open Questions

### Risks

1. **FIX-01 may expose secondary bugs:** If Hi-Z was never actually working after resize (because the app crashes or validation layers catch it first), fixing it may reveal rendering artifacts from incorrect Hi-Z data on the first post-resize frame.

2. **FIX-02 requires careful frame tracking:** The double-buffered scratch buffer approach must stay synchronized with `Renderer::current_frame`. If the frame index is ever modified outside the expected pattern, buffers could be freed prematurely.

3. **FIX-03 changes `run_frame` signature:** This touches the scheduler, which has tests that call `run_frame` with mock data. Tests will need updating.

### Open Questions

1. **Should FIX-10 be included?** The one-shot fence change is low priority and the current `queue_wait_idle` works. Including it adds risk for minimal benefit since we only have one queue.

2. **Should we add GPU validation error counting?** A counter that tracks validation layer errors per frame would be useful for automated testing but adds complexity.

3. **Are there any shader bugs exposed by the cull shader reading stale Hi-Z data?** The Hi-Z pipeline uses 1-frame temporal latency (D-04), so the first frame after resize always has stale data. This is by design, but the stale data is from a destroyed image post-resize.
